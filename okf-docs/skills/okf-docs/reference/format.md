# Format

OKF v0.3 plus a few extension keys. A concept is a `.md` file with frontmatter and a non-empty `type`; OKF asks for nothing else. The rest is house style that makes bundles rankable and checkable. Other OKF tools ignore the extensions.

## Bundle

```
<bundle>/
├── index.md        # listing; generated by `okf.py index --write`
├── log.md          # change history, newest date first; written by `okf.py log`
└── <folder>/
    ├── index.md
    └── <concept>.md
```

- `index.md` and `log.md` are reserved at every level and are never concepts. `log.md` has no frontmatter. Only the bundle-root `index.md` has frontmatter (below); a subfolder `index.md` has none.
- Every other `.md` file with a `type` is a concept. A file without one (`README.md`, `AGENTS.md`, `CONTRIBUTING.md`, notes) is not a concept: OKF consumers skip it. Don't put a `README.md` in a bundle; `index.md` is the entry point. Dot-files and dot-folders are not part of the bundle.
- Create a folder only when a file goes in it. Folder entries in an index carry a one-line description you write; the script keeps it.
- Names: `kebab-case.md`. Decisions: `NNN-short-title.md`, three digits. Observations and assets start with their date: `YYYY-MM-DD-slug.md`.

## Frontmatter

```yaml
---
type: concept
title: Data export
description: Export a workspace as CSV or JSON; runs as a background job, 500 MB limit.
tags: [export, jobs]
x-okfdocs-scope: acme-api/export
x-okfdocs-specificity: specific
generated:
  by: okf-docs/1.0.5
  at: 2026-11-12T14:03:22+01:00
verified:
  - by: human:alex
    at: 2026-11-12T16:40:00+01:00
    x-okfdocs-via: review
sources:
  - id: job
    resource: ../../src/export/job.ts
    author: human:alex
  - id: d004
    resource: ../decisions/004-export-format.md
---
```

The `x-okfdocs-*` keys are this plugin's own, prefixed as OKF 0.3 §4.1 asks for extension keys. Older bundles use the unprefixed 0.9 names (`scope`, `specificity`, `class`, `visibility`, `supersedes`). `okf.py upgrade` renames them, and check still reads them (finding `legacy-key-name`). Versions before 1.0.4 also wrote `x-okfdocs-credibility` (`reported` or `inferred`): it is retired (`credibility-retired`), because OKF 0.3 records where content came from as source signals, not as a label, and upgrade removes it. In prose, "visibility" or "class" is the concept; in a file it is always the full key.

| Key | From | Rule |
|---|---|---|
| `type` | OKF, required | Lowercase house type from the bundle's kind file. Any string is valid OKF |
| `title` | OKF | House: required |
| `description` | OKF | House: required. One sentence with the most useful fact, never "This document describes…". Feeds `index.md` |
| `resource` | OKF | Canonical URI of the thing described (endpoint, table, repo), when there is one |
| `tags` | OKF | A YAML list of tags someone would filter by. A scalar counts as one tag and is never split at commas (check: `tags-format`) |
| `sources` | OKF | List of entries. Each needs `resource` (path or URL; `source-no-resource` otherwise). Optional: `id` (unique in the file; the body cites it), `title`, `author` (an actor), `last_modified`, `usage_count` with `usage_window` (`from`, `to`; `usage-window-missing` otherwise) |
| `generated` | OKF | `by` and `at` of the last meaningful change. Bump `at` when facts change, not for typo fixes. This is what makes older `verified` events non-current |
| `verified` | OKF | List of `by` and `at` entries: who confirmed the content and when. Keep old entries as history. Only entries with `at` on or after `generated.at` count (current); when facts change, bump `generated.at` and the old ones stop counting. A `human:` entry also gets `x-okfdocs-via`: `chat` (the person said so in a session) or `review` (they confirmed it in the review queue); other values: `via-value` |
| `status` | OKF | `draft`, `stable` or `deprecated`; anything else is not current (`status-value`). `deprecated` when kept only for links or history. Absent means current. Don't write `draft`: a file with no human `verified` entry is unreviewed, and a second marker can disagree with it. Keep `draft` where another tool set it, and remove it when a human verifies the file |
| `stale_after` | OKF | Instant after which the content is stale: an offer valid to a date, an observation to re-check. A date is fine; one that doesn't parse counts as stale (`stale-after-format`) |
| `x-okfdocs-scope` | extension | The subject, broad to narrow, `/`-separated (`acme-api/export`). Absent means the bundle's root scope from config. The parent of `a/b` is `a` |
| `x-okfdocs-specificity` | extension | `general` (a whole product or area), `specific` (one feature or process), `exact` (one limit, field, endpoint or rule). Scope fit, never length |
| `x-okfdocs-class` | extension, brain | `canonical`, `decision`, `observation`, `asset`, `reference` or `tracker` |
| `x-okfdocs-visibility` | extension | `internal` (default) or `public`. Only public files may feed public pages |
| `x-okfdocs-supersedes` | extension | Path of the file this one replaces. Decisions and deprecated files only |
| `superseded_by` | OKF | Path of the replacing file. Only with `status: deprecated` (`superseded-not-deprecated` otherwise) |

Keep keys other tools added; never strip them.

## Values

- **YAML style:** mappings in block style, one key per line, as above. Inline lists only for plain words (`tags: [export, jobs]`). Older YAML parsers (libyaml before 0.2.2, which macOS's system Ruby still uses, and PyYAML before 5.1) reject a timestamp or `human:alex` inside `{ }` or `[ ]`; `okf.py check` warns about it.
- **Timestamps:** write date-times with an offset for `generated.at` and `verified[].at`: `2026-11-12T14:03:22+01:00` or `2026-11-12T13:03:22Z`. Use `NOW` from the context output or `okf.py now`. A bare date is valid OKF (start of that day, UTC) and fine for `stale_after`, `last_modified` and `usage_window`; for `generated` and `verified` check warns `timestamp-date-only`. A date-time without an offset is invalid.
- **Actors:** `human:<id>` for a person, with the id that `okf.py now` prints. It comes only from `OKF_ACTOR` or `git config okf.actor`. When it prints "human: not set", it may add a suggestion from `git user.name`: ask the person to confirm it or give another, then save it with `git config --global okf.actor <id>` once they agree, so it's asked once per machine. Never write an id the person hasn't confirmed, and never take one from the login name or email; `team:<id>` for a group (counts as machine-confirmed, not human-reviewed); `process:<id>` for automation; `okf-docs/<version>` for what you write; any other tool as `<tool>/<version>`. `sources[].author` is an actor too.
- **Empty values:** null, an empty string and an empty list mean the key is absent. Frontmatter is YAML 1.2 (core schema), so `yes`, `no`, `on` and `off` are text; YAML 1.1 tools such as PyYAML read them, and values like `1:20` or `010`, differently. Quote values that look like numbers or booleans (`okf_version: "0.3"`); check warns about each unquoted one with `yaml-quote`. Duplicate keys are an OKF error (`duplicate-key`).
- **Sources and footnotes:** cite a claim with a footnote whose label is the source `id`:

  ```markdown
  Exports over 500 MB fail with `EXPORT_TOO_LARGE`.[^job]

  [^job]: src/export/job.ts
  ```

  A footnote label without a matching `sources[].id` is flagged (`footnote-no-source`). Add `author` when you know who stated it: `human:alex` for a meeting asset, `team:finance` for a policy page. This is how a file says it reports what a person said; an inference of yours says so in the body ("Inferred from …"). A plain description such as `pasted in conversation, 2026-11-12` is allowed when there is no file: what someone told you in a session is `resource: conversation with <name>, <date>` with their `author`. A source you only summarized needs an entry but no footnote.
- **Paths and links:** a path without a leading `/` resolves from the file's directory (`../schema/exports.md`); with a leading `/` from the bundle root (`/schema/exports.md`). Both are valid OKF. Relative is the default because it works on GitHub, in editors and in site generators; set `links: rooted` in config to write rooted ones. Path fields: `resource`, `sources[].resource`, `superseded_by`, `x-okfdocs-supersedes`. In a bundle that declares 0.2 or no version, a bare path that only resolves from the root is flagged (`path-root-fallback`); upgrade fixes it. Percent-encode spaces; paths are case-sensitive. A target outside the bundle root is external: other OKF consumers must not read it. This plugin still reads repo files for staleness (`../../src/export/job.ts`), so keep such sources. Link another bundle by its URL from `related` in config.

## Reserved files

`index.md`. The bundle-root one starts with frontmatter; subfolder ones have none:

```markdown
---
okf_version: "0.3"
title: Acme API docs
description: Product and API behavior for the Acme API; use it to answer how the API works.
---

# Sections

* [Product](product/) - What it does: features, behavior, limits.

# Concepts

* [Data export](export.md) - Export a workspace as CSV or JSON; runs as a background job, 500 MB limit.
```

The root frontmatter has `okf_version: "0.3"`, `title`, `description` (the scope of the bundle and when to use it; check: `root-index-meta` if missing) and an optional `license` (SPDX expression or a path to a license file). Entries come from each file's `title` and `description`. Regenerate with `okf.py index --write` rather than editing entries by hand; root frontmatter, headings, order and folder descriptions you edit are kept.

`log.md` has no frontmatter (OKF error `log-frontmatter`):

```markdown
# Directory Update Log

## 2026-11-12
* **Creation**: [Data export](product/export.md).
* **Deprecation**: [CSV export v1](product/csv-v1.md), replaced by [Data export](product/export.md).
```

Headings are `## YYYY-MM-DD`, newest first. Add entries with `okf.py log <bundle> <Kind> "<message>"`. Kinds: Initialization, Creation, Update, Deprecation, Deletion, Decision, Sync, Publication, Review (a brain review, check.md). The newest Review entry dates the `BRAIN_REVIEW` count.

## OKF errors and house rules

`okf.py check` labels each finding:

- **OKF error:** the bundle is non-conformant (OKF §11.1): frontmatter that isn't a YAML mapping, duplicate keys, frontmatter in a non-root `index.md`, frontmatter or bad date headings in `log.md`. Fix these first. Exit code 1 means OKF errors only.
- **OKF warn:** shape problems other consumers ignore or misread: a file with no `type` (`not-a-concept`), malformed timestamps, actors, `sources` or `verified`, bad `status`, paths that don't resolve, an old `okf_version`.
- **House:** this plugin's conventions. Titles and descriptions, naming, index coverage, extension values, link style, legacy key names, date-only `at`.
- **Content:** broken links, stale, unverified or `verification-outdated` files, duplicates, bloat, deletion candidates.

## Trackers

`x-okfdocs-class: tracker` marks a living list in a brain: `actions.md` (`type: action-list`) and `questions.md` (`type: question-list`) at the bundle root. Frontmatter is `type`, `title`, `description`, `x-okfdocs-class` and `generated`; no `sources`, no verification. Check skips them for review, decay, staleness, duplicates, deletion and source checks. The body has an `## Open` table and a `## Done` (actions) or `## Answered` (questions) table, in the exact columns of templates/brain.md; dates are YYYY-MM-DD and `Due` may be `-`. Both actions tables may have a `Ticket` column right after `Action`: the ticket's link, `-` when the action needs none, or empty when it isn't synced yet.

Findings: `action-overdue` (content, info): an Open action is past its Due date. `tracker-format` (house, warn): the Open table is missing or its header doesn't match. `tracker-prune` (house, info): Done or Answered rows older than 90 days. With `brain.tickets` on: `action-unsynced` (content, info), an Open action with an empty Ticket cell; `tracker-format` (house, info), an actions file with no Ticket column. A bad `brain.actions`, `brain.names` or `brain.tickets` value, or a `hooks.*` switch that isn't true or false (yes/no and on/off also work), falls back to the default: `config-value` (house, warn) in check, `CONFIG_VALUE` in context.

Brain settings in `.okf/config.yaml`: `brain.actions` (`report`, `track` or `off`; default `report`), `brain.names` (`team`, `roles` or `all`; default `team`), and `brain.tickets` with `system` (the ticket system's name, such as `linear`, `jira` or `github`, or `none`; default `none`) and `target` (the team, project, board or repository). Ticket sync is on when `system` isn't `none` and `brain.actions` isn't `off`. For `github`, context also says whether the `gh` CLI may stand in for a connector: only in a git repository with a GitHub remote. Invalid values fall back to the default (ticket sync off) and are reported.

## Brain review and history

`## History` in an entity file (customer, client, product, initiative) lists one line per meeting, decision or observation, newest first: `- 2026-11-20 [Follow-up call with Globex](../../assets/2026-11-20-globex-follow-up.md): audit trail need`. Write it with `okf.py history <entity file> <asset file> --note "<a few words>"`, which dates the line from the asset's file name (the meeting date), changes only that section and skips an asset already listed. A history line is not a change of meaning: it leaves `generated.at` alone (OKF 0.3 §5.2).

Finding `generated-not-bumped` (content, warn): in git, the file's title, description or body outside `## History` changed since the last commit, a verification still counts, no new one was added, and `generated.at` didn't move. Bump `generated.at` unless the edit was trivial (typo, format, link repair); whitespace changes and history lines don't trigger it.

Finding `promotion-candidate` (content, info): an observation whose `sources` cite two or more distinct resources; propose promoting it (lifecycle.md, Promotion). The context directive `BRAIN_REVIEW: <N> assets added since the last brain review (<date or never>)` appears when N is 3 or more.

Config `hooks.capture` (default `false`): the Stop hook reminds the agent once per session, after real work, to capture knowledge (write.md, Capture).

## Attested Computation

`type: Attested Computation` (OKF §10) is a concept with runnable code. Check recognizes it: it expects `runtime`, a computation (a `computation` path, or exactly one fenced block under a `Computation` heading) and `parameters` entries with `name` and `type`, and notes when there is no `attester`. Don't write one unless the user asks. Never edit its computation code; only the user changes it.

## Upgrading

`okf.py upgrade --dry-run` lists the changes for any older format; run it without `--dry-run` once the user approves. It rewrites changed files, not the rest.

### From okf-docs 0.9 (OKF 0.2)

1. Rename the keys: `scope`, `specificity`, `class`, `visibility`, `supersedes` get the `x-okfdocs-` prefix, same position and value. Remove `credibility` and `x-okfdocs-credibility` (`reported` or `inferred`); for a `reported` file whose sources name no `human:` author, the report suggests adding who stated it.
2. Set root `okf_version: "0.3"`; keep the other root keys. Add `title` and `description` to the root `index.md` if they're missing (ask the user for the description).
3. Turn date-only `generated.at` and `verified[].at` into date-times (`2026-09-05T00:00:00Z`).
4. Fix bare paths that only resolve from the bundle root (`path-root-fallback`), in the bundle's link style.
5. Drop frontmatter from `log.md`. Make scalar `tags` a list; a comma-separated one is split only here, and the report says so.
6. Report files whose trust dropped because their `verified` events are older than `generated.at`: they need a re-check.

### From the v3 skills

The older standalone okf-docs and okf-company-brain skills wrote a v3 format. Everything in the 0.9 list applies too; v3 also changes:

| v3 | Now |
|---|---|
| `at: 2026-09-05` | `at: 2026-09-05T00:00:00Z` |
| `by: agent` | `by: okf-docs/3` |
| `by: alex` | `by: human:alex` |
| `sources: [src/x.ts]` | Entries with `resource`, paths made relative to the file |
| `credibility: verified` | Removed (under either key name) where a human `verified` entry records the review. Without one, upgrade lists the file: ask who confirmed it, then add the entry or remove the key |
| `credibility: reported` or `inferred` | Removed, as in the 0.9 list |
| `links: [...]` | Moved to a `## Related` list in the body |
| Frontmatter in folder `index.md` files | Removed. The root keeps `title`, `description` and `license`; v3-only concept keys there are dropped and reported |
| Promoted observations kept with `superseded_by` | Deleted after approval (check lists them) |
| A page in a folder's `index.md`, such as `products/waycam/index.md` | Moved to `products/waycam/waycam.md` after approval, with links repointed; then the index is rebuilt. upgrade, `check --fix` and `index --write` never rewrite such a file (check: `index-page`) |

The v3 rules also have to go, or Claude follows two formats. Context reports them as `LEGACY_SKILLS` (installed skills) and `LEGACY_RULES` (copies in the project's `.claude/skills/`, and `CLAUDE.md` or `AGENTS.md` lines such as "no `status` field" or `credibility: verified`). Propose retiring them in the same plan as the upgrade; change nothing before the user approves.
